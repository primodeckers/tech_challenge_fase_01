ML Canvas — churn Telco

Tech Challenge · Fase 1. Caixas no espírito do Machine Learning Canvas (Louis Dorard / OWNML). Texto canônico em ml_canvas.md; quem mudar um arquivo alinha o outro para o grupo não ler versões diferentes.

End-user quem usa / quem é afetado

Direção e dono de produto querem menos churn sem estourar o orçamento de campanhas. Marketing e CRM querem listas priorizadas e mensagens que não chateiem quem não ia sair. Operações e call center precisam de filas realistas — não dá para tratar sete mil pessoas na mesma semana. A equipe de dados entrega pipeline, MLflow e API. Jurídico só faria falta em produção com dados reais; aqui é exercício com dataset público.

Value proposition o que fazemos pelos usuários

A operadora perde clientes por cancelamento. Retenção costuma ser mais barata que aquisição, por isso o valor do sistema é priorizar quem tem mais probabilidade de sair, para concentrar contatos ou ofertas onde o retorno compensa, em vez de ir à sorte na base toda.

O modelo deve produzir risco de churn (probabilidade ou classe) para alimentar CRM ou filas de call center, com revisão humana nos casos limítrofes (regra de negócio a fechar).

O Excel não traz insatisfação subjetiva, falhas de rede ou mudança de cidade — o modelo trabalha com o que há.

Data sources de onde vêm os dados

  • Arquivo data/raw/Telco_customer_churn.xlsx no repositório (IBM-style Telco churn, uso acadêmico).
  • Em uma operadora real entrariam bases internas de billing, CRM e possivelmente APIs de terceiros; não é o nosso caso neste challenge.

Problem especificação do motor de predição

Pergunta que o modelo responde: este cliente tende a cancelar nos próximos tempos (no sentido captado pelo rótulo histórico Churn Label)?

Entrada (input): linha de cliente com variáveis tabulares (serviços, contrato, cobranças, tenure, etc.), no schema fechado depois do pipeline (o que fica de fora, o que é numérico, o que vai a one-hot).

Saídas possíveis: probabilidade de churn ou etiqueta Yes / No conforme um limiar ligado ao custo FP/FN (ver Performance evaluation).

Tipo de problema: classificação binária supervisionada.

Baseline simples (alternativa ao ML): regras manuais do tipo “contrato month-to-month e tenure baixo → risco alto”, ou previsão constante (Dummy); no código: DummyClassifier e regressão logística antes da MLP.

Data preparation treino e features

Ordem de grandeza: ~7k linhas, 30+ colunas — volume modesto, mas dá para treinar e comparar modelos sem drama. Alvo: Churn Label (Yes / No); no EDA a classe Yes rondava cerca de um quarto da base (desequilibrada, mas não raríssima). Vale medir de novo depois de tratarmos as linhas em que Total Charges não convertia para número (poucas, mas não zero).

Features: serviços, contrato, encargos, tenure, composição do agregado, etc. Cuidado com leakage: Churn Score, CLTV, Churn Reason cheiram a informação post hoc — o default do grupo é não usar como input até alguém confirmar o timing em documentação de negócio.

Performance evaluation como medimos sucesso

Valores fechados (razão FP/FN, limiar, métricas): docs/metricas_e_limiar.md. Aqui fica o resumo.

Métricas de negócio (bottom-line, a quantificar): custo de falso negativo (perdemos a retenção) vs. falso positivo (contato inútil, desgaste). Sem contabilidade fina no enunciado, usamos razões FP:FN plausíveis (ex.: “1 FN custa o dobro de 1 FP”) e documentamos no Model Card. Accuracy sozinha não conta — com muitos No na base dá para parecer bom sem aprender.

Métricas de precisão da predição: ROC-AUC para comparar entre si; PR-AUC e F1 na classe Yes (classe minoria); Brier só se formos usar a probabilidade para cortes finos.

Avaliação offline: validação cruzada estratificada, seed fixo, mesma lógica para baselines e para a MLP mais tarde.

Em produção (rascunho): taxa de churn entre clientes de alto risco, estabilidade das distribuições de features (drift), predições falhadas — encaixa no plano de monitoramento que ainda vamos fechar no fim do trabalho.

Using predictions integração

Quando e quantas: batch diário ou sob pedido; o challenge inclui FastAPI, por isso o desenho principal é sob pedido.

Restrição de tempo: p95 do POST /predict na ordem de meio segundo com payload típico; cold start documentado se for relevante.

Uso de predições e confiança: filas por score decrescente; limiar ajustável quando o custo FP/FN mudar.

Sem predição a tempo: fallback (regra simples ou “não priorizar”) — detalhar no desenho da API.

Learning models treino e deploy

Quando treinar ou refrescar: após janelas de dados fechadas ou quando o drift passar um limiar; no trabalho nos focamos numa versão entregável.

Tempo de treino: aceitável em minutos neste volume; MLP com GPU opcional.

Critério para “subir” modelo: melhoria clara em PR-AUC ou F1 no Yes em relação ao baseline logístico, sem degradação grave na matriz de confusão ao limiar escolhido; MLflow com commit Git e referência ao arquivo de dados.

Riscos e limitações

Base histórica pode não representar novos produtos ou regiões. Quem atende o telefone vai querer saber por que o cliente ficou marcado como risco — um score sozinho não chega; mais tarde pode ser preciso importância de variáveis (há quem use SHAP) ou regras simples por canal, se o negócio pedir. Os dados do exercício trazem identificadores e endereço; num cenário real entraria legislação de proteção de dados (LGPD / GDPR) e minimização de dados.
